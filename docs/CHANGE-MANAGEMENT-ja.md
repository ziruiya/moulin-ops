# 変更管理

## 計画の進行

```text
DRAFT → ASSESSMENT → TESTING → PENDING_APPROVAL → APPROVED → SCHEDULED
  → EXECUTING → VERIFYING → COMPLETED
```

| 段階 | サーバーで確認する条件 |
| --- | --- |
| 起票・影響調査 | 影響範囲、関連資産、対象コンポーネントを記録します。対象外の資産のコンポーネントは関連付けできません。影響調査と必須項目を済ませてから `TESTING` へ進みます。 |
| 承認待ち | テスト計画と事前検証の合格証跡が必要です。必須項目の不足は承認待ちへの遷移を止めます。 |
| 承認・実施予定 | 独立した Reviewer の承認を確認します。担当者と予定枠を記録します。承認と差し戻しにはログイン中の実際の承認者 ID、日時、決定、コメントが残ります。差し戻し `REJECTED` から影響調査に戻して再提出できます。 |
| 実施開始 | バックアップの参照と検証、復元テストの合格、有効な予定枠、担当者、準備段階までの必須項目を確認します。高リスクの実施者は指定の Operator です。承認した本人は実施担当になれません。 `actual_start_at` は実施を記録した時刻です。 |
| 動作確認・完了 | 実施項目と実施後の必須確認を済ませます。完了時に検証結果と `actual_end_at` を記録し、予定枠を保持します。 |
| 緊急変更 | `Emergency` を区別して扱います。通常の実施ゲートと確認を経て、事後レビュー結果を記録した場合に `VERIFYING → EMERGENCY_REVIEW` に進めます。 |

五段階は影響調査、事前検証、バックアップと復元準備、実施、実施後の確認です。必須項目が合格するか、適用範囲と理由を記入した Reviewer の免除が必要です。免除は記録した項目に適用し、他の行の判断を省略しません。不合格の項目を再検証するときは、是正理由と新しい証跡を添えた合格の行を元の項目にひも付けます。

条件に不足があって保留した場合、`BLOCKED` に入る直前の状態を保存します。再開先はその状態です。取りやめた変更は `CANCELLED`、実際に失敗した変更は `FAILED` として扱います。

## 承認と役割の分離

Reviewer は発起人・実施担当者のどちらとも異なるユーザーです。Policy で役割と独立性を判定し、DB の CHECK でも自分への承認を拒否します。Operator と Reviewer の兼任者が承認する場合は Admin が付与理由を保存した承認権限が必要です。差し戻し後は再提出の判断を新しい承認行に追加します。 [権限と監査](SECURITY-ja.md)

## ロールバックと障害

```text
EXECUTING → FAILED → ROLLBACK_REQUIRED → ROLLING_BACK → ROLLED_BACK
                                                   └→ ROLLBACK_FAILED
```

- トリガーは、起動不能、DB 接続失敗、主要業務の検証失敗、予定枠の超過などを作業前に決めます。実施失敗から直接 `COMPLETED` には遷移できません。
- `ROLLED_BACK` は旧版での復元と再検証を記録した状態です。ロールバックの理由と、復元後の Web・アプリケーション・DB・業務の確認結果を記録します。実績終了時刻、復元作業、関連障害の結果を追跡できます。
- `ROLLBACK_FAILED` では失敗の根拠と調査対象が残ります。計画の状態変更と関連障害の作成を同じ DB トランザクションで行い、障害作成に失敗した場合は計画・作業・監査への書き込みを巻き戻します。運用上の再調査と復旧は障害側で継続します。
- 障害を閉じるには、復旧結果、検証、関連作業、閉じる理由、後続計画の要否を確認します。高リスクの場合は解決担当と別の検証者および検証日時を記録します。低リスクでの自己検証は明示し、監査に残します。

デモの `CHG-2026-001` は事前検証とバックアップを記録済みで、復元未確認のため実施が止まる例です。`CHG-2026-002` は完了、`CHG-2026-003` はロールバック失敗を記録しています。画面の実施・復元は担当者が検証した内容の記録です。 [面接官向けガイド](INTERVIEW-GUIDE-ja.md)
